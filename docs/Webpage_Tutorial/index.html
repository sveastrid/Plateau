What a player sees, and which code runs

MRBoardGame2 is a colocated mixed-reality board game for Meta Quest. Several people stand around one real table in one real room, each wearing a headset. Passthrough is on, so they see each other's real faces and hands. The only virtual parts of another player are two controller cones and a floating nametag. On the table sits a virtual board that everyone sees in the same place. Anyone can move, turn and resize it by squeezing both grips and pulling the air.

One platform hosts three games. It handles joining a room, lining the headsets up on the same physical room, voice, the shared board frame, the two-grip grab, where players stand and the menu. Walking through one session is the quickest way to meet every major part of the code:

Five assemblies, and why the boundary is the point

Each folder with an .asmdef compiles into its own DLL, and an assembly can only use types from the assemblies it lists. Here is the whole of BASH's list:

MRBoardGame.Shared is there, and MRBoardGame.Plateau and MRBoardGame.Stairs are not. Stairs and Plateau have the same shape. Shared's own list has eighteen entries — Netcode, the XR packages, Unity Gaming Services, URP — and none of them is a game. The Editor assembly references Shared and is compiled for the Editor only ("includePlatforms": ["Editor"]).

Why go to the trouble? Because a boundary the compiler enforces catches coupling the moment it is written, not later in a headset. The split caught a real bug on its first compile. BASH's ControlListener.Bind() was calling PlateauBoard.FindDescendant, borrowing a utility from inside another game. While everything lived in one assembly that compiled silently; after the split it was an error. The helper now lives in Shared as HierarchyUtils.FindDescendant (Module 3), which also let four identical private copies be deleted. A second benefit: editing one game recompiles only that game's assembly.

The rule for you

If you find yourself needing to read a second game's code to change the first, stop: that is a coupling bug, not a task. Shared code that needs to know something about a game asks through IGameSession. Also note there are no namespaces: every class is in the global namespace. So a class name that collides with a type in a referenced assembly is a real hazard. HierarchyUtils is not called Hierarchy because Unity 6 added a Unity.Hierarchy namespace.

Two clocks

Two clocks run through this project, and most of its subtler bugs come from mixing them. Unity's frame runs Update every rendered frame: 72–90 times a second on a Quest. Netcode's tick is when replicated state actually goes out on the wire: 30 times a second here. So a value written in Update reaches other headsets at tick rate, which is why remote avatars and the board are smoothed on arrival rather than set raw (Modules 11 and 13).

The Unity lifecycle, as used here

  • Awake runs when the object is created. This project uses it to set Instance singletons and to construct NetworkLists, which must exist before Netcode spawns the object.
  • Start runs once, before the first Update. For an object that survives scene loads (anything under PersistentRig, or the Network Manager), that means once per app launch, never once per scene. Code that must re-run on every game switch hangs off SceneManager.activeSceneChanged instead.
  • Update and LateUpdate run every frame. Their order across components is undefined unless a class declares [DefaultExecutionOrder(n)]; lower runs first. Fourteen components here declare one, and the values are load-bearing (Module 15).
  • OnDestroy is where subscriptions are removed and singletons cleared.

Static fields outlive scenes. They also outlive a Play session when the Editor's domain reload is switched off. So any static that describes a session has to be reset on purpose. BoardAnchor does it in Awake, which runs once per launch, in the lobby:

A serialized value beats the field initializer

A public or [SerializeField] field's value is saved into every scene and prefab that uses the component. When Unity loads the object, the saved value wins over the = 0.6f written in the .cs file. Raising a default in code therefore changes nothing for an object that already exists. CameraController2's height guard is the example in this project: PersistentRig.prefab carries its own copy, and that copy is what runs. Renaming a serialized field is worse: every saved value is silently dropped. This is why several components re-find a null reference in Start(). Treat that as the pattern, not as belt and braces.

Host, server and client

There is no dedicated server. The room owner's headset calls StartHost(), which makes it both the server and a client; everyone else calls StartClient(). "Validated on the server" therefore means "validated on the room owner's headset". In code you ask IsServer, IsClient, IsHost and IsOwner. Client ids are ulongs, and the host's own client id is 0. NetworkVariable: who may write is the security boundary

A NetworkVariable<T> is a replicated field. Its writer's value is sent to everyone at the tick, whenever it has changed. Every declaration names who may read it and who may write it, and in this project the write permission is the security boundary. The avatar shows both kinds side by side:

Hand and head poses are Owner-written: you are the authority on where your own hands are, and nobody else needs to trust that beyond drawing a cone. Anything others must be able to rely on is Server-written: your place on the ring, your name, whether you own the room. A client that writes a server-written variable gets an error, and nothing changes.

Two behaviours of NetworkVariable recur throughout the course:

  • The setter only sends a change. Assigning the value a variable already holds marks nothing dirty, so no client hears about it. When "it happened again" matters, the project bumps a counter instead. PlateauGame.chooserResultEpoch exists because a spin can land on the same answer twice.
  • OnValueChanged is not raised for the value a client arrives holding. A late joiner's first value just appears. So the first value has to be applied by hand, before subscribing:

NetworkList: the same trap, for collections

A NetworkList<T> replicates a list of small structs and sends only the changes, one delta per add, remove or set. Its initial contents arrive with the spawn and raise no OnListChanged at all. Both boards that store their state in lists therefore treat any change as "the board is dirty". RPCs: anyone may call, the server checks who did

A ServerRpc is a method a client calls that then runs on the server. By default only the object's owner may call it. GameSelector lives on each player's own avatar, so that default fits: you may only ask for a game switch through your own player object.

Shared objects like Room Anchor belong to the server, so their RPCs say RequireOwnership = false: any client may call them. The method then decides whether this caller is allowed. Two details you will trip over

The compiler warns CS0618 on every RequireOwnership, because Netcode 2.x prefers its newer [Rpc] attribute. These warnings are pre-existing and harmless. Separately, an RPC goes out as soon as it is called, while a NetworkVariable change goes out at the end of the tick. The two do not arrive in the order you wrote them, which is exactly the bug BASH hit (Module 21).

Scenes under Netcode

With scene management on, only the server changes scenes: it calls NetworkManager.SceneManager.LoadScene, and every client follows. A client that joins later is synchronised into whatever scene the room already has open. Spawned objects that were not created with the scene are carried across the switch. So a client must never call Unity's own SceneManager.LoadScene during a session: it would leave the room's shared scene behind. Module 6 walks through the one place that changes scenes.

The join handshake hashes your build

ForceSamePrefabs: 1 folds every registered network prefab's identity hash into a config hash that a joining client sends. The server compares it with its own and refuses any difference, with no reason string. The joiner just sits on "Joining room…". Editing Player.prefab changes that hash, and so did turning connection approval on. Hence the project's most repeated instruction: flash both headsets from the same build, every time. Module 16 covers the guard that keeps foreign prefabs out of the list.

XR in brief

The rig is Unity's XROrigin: a root the app may move, a Camera Offset child, and a camera and hands that the headset drives inside it. The tracking origin mode is Floor: y = 0 is the headset's estimate of the real floor, and each headset estimates it separately. Controllers are read through UnityEngine.XR.InputDevices (Module 4). Two Meta pieces appear later: OVRSpatialAnchor, a point in the real room that several headsets can find (Module 12), and OVRPassthroughLayer, the camera feed drawn behind the app (Module 14).

The house rules

These are the conventions every networked script here follows. Later modules show each one in context.

  1. Server-written is the security boundary. Shared state is only ever written by the server.
  2. Every mutating ServerRpc validates its sender, bounds-checks every index, and clamps every count.
  3. The client's highlight is a hint; the server re-runs the rule. Each game keeps one rules class (StairsMoveRules, PlateauMoveRules) that the client uses to light legal moves and the server uses to accept them, so the two cannot disagree.
  4. No local prediction, except for state a client holds an exclusive, server-granted lock on (only the world grab).
  5. Pieces are local visuals rebuilt from replicated state. A piece is not a NetworkObject, because 160 pieces would mean 160 spawn messages, and every new network prefab moves the join hash.
  6. Seats are handed out by polling at 4 Hz, not in a connect callback, because a player's ring slot is assigned later, when their avatar spawns.
  7. Instance singletons are set in Awake or OnNetworkSpawn, and cleared in OnDestroy or OnNetworkDespawn behind if (Instance == this), because a replacement can arrive before the old one leaves.

Solution

Player B calls RoomAnchor.SetContentServerRpc while player A holds the world. What happens?

  • The server applies B's pose; the last writer wins

  • So that voice defaults to on for new rooms

A late joiner's initial value appears without an event. Without the explicit call, someone joining a room with voice already on would stay silent. The same trap exists for NetworkList contents.

Two headsets were flashed from different builds; one of them includes an edit to Player.prefab. The joiner stays on "Joining room…", and the disconnect reason is empty. Why?

An empty DisconnectReason is the signature of the config-hash refusal. A protocol mismatch fails too, but at the transport level, and Relay would have rejected a bad code outright. Reflash both headsets from the same build.

The server does chooserMaterialIndex.Value = 2 when the value is already 2. What do clients observe?

  • OnValueChanged(2, 2) fires on every client
  • The whole object is re-sent
  • An exception on the server
  • Nothing: the setter only marks the variable dirty when the value differs

That is why PlateauGame also bumps chooserResultEpoch. A counter that only ever increases cannot equal its previous value, so clients are always told that a spin resolved.

Why must a NetworkBehaviour override OnDestroy and call base.OnDestroy(), rather than declaring its own void OnDestroy()?

Show model answer

Netcode declares OnDestroy as virtual on NetworkBehaviour and does its own teardown there. A plain void OnDestroy() hides that method instead of overriding it; the compiler only warns. Netcode's teardown then never runs, and the behaviour's registration with its NetworkObject leaks. StairsGame is the class in this project that needs it.

What is the difference between "the host" and "the server" in this project? And why is RoomAnchor.NoHolder ulong.MaxValue and not 0?

Show model answer

The host is one headset, the room owner's, running both the server and a local client (StartHost). There is no dedicated server, so every "server-side" check runs on that headset. Client id 0 is the host's own id, so 0 cannot mean "nobody". ulong.MaxValue is never a real client id.

The smallest script in the project does one of its most important jobs:

PersistentObject sits on the root of Assets/Prefabs/PersistentRig.prefab. Exactly one instance of that prefab exists, in OpeningScene. DontDestroyOnLoad moves it out of the scene, so every later LoadSceneMode.Single game switch leaves it alone. The prefab holds everything a player is locally:

Before this prefab existed, every game scene baked in its own full rig, and each game switch destroyed and rebuilt all of it. Now game scenes contain no rig at all. A second object with any of these names in a game scene is a bug: GameObject.Find would pick one of the two unpredictably.

Do not "fix" the resting position

The prefab root sits at (0, 0, -10). That is where the lobby's original rig was hand-placed, facing its panels. In game scenes CameraController2.PlaceAtRingSlot moves the rig to the player's place on the ring (Module 11), so the baked value only matters in the two scenes that never do that: OpeningScene and the legacy GameScene. Moving it somewhere that looks sensible for a game breaks the lobby.

Game scenes are thin

A game scene's hierarchy is World Root → Board → the game's geometry, with the board at the origin. World Root carries RoomContent and is the content frame: everything the game owns hangs under it, and nothing a player owns does. That is what lets the two-grip grab move and resize "everything except the players" by moving one transform (Module 13). A game may also add a scene-root controller object beside World Root, such as Stairs Controller or Plateau Controller, for scripts that read input but own nothing in the frame.

Two ways a name breaks

Renamed: since PersistentRig, there is exactly one instance of each name, so a rename fails everywhere at once, in every scene. Most lookups are null-guarded and just degrade quietly. Two are not:

RHController and LHController chain .GetComponent onto a Find that may return null, so a missing Input Reader throws a NullReferenceException right here. Duplicated: two objects with the same name make Find return whichever it meets first. Different scripts can then bind to different instances, and the scene's copy dies at the next switch.

What survives a game switch

A game switch is LoadSceneMode.Single: Unity destroys everything in the outgoing scene except objects that were moved out of it. This diagram shows the whole of what survives:

Anything that survives but caches a scene object has to re-find it after a switch. Here is who does:

  • PlayerControls.BindToScene() runs on SceneManager.activeSceneChanged (Module 11).
  • MenuControl.AdoptSceneDefaults re-applies the pointer default for the new scene on the same event (Module 10).
  • BoardAnchor.HandleActiveSceneChanged clears its cached rig references and re-finds them next frame (Module 12). It is now a harmless no-op, because the rig never changes; it is kept so a future scene that brings its own rig still degrades safely.
  • CameraController2.AdoptLocalPlayerSlot() runs in Start(), for when the rig comes up after the player object.

Note activeSceneChanged, not Start(). A persistent object's Start runs once per launch, in the lobby, and never again.

A component on PersistentRig caches GameObject.Find("World Root") in Start. After the first game switch it throws MissingReferenceException. Explain why, and give the fix this project would use.

One reader, plain fields

The project uses Unity's device-level XR API (UnityEngine.XR.InputDevices) and the legacy Input class for the keyboard. The new Input System is deliberately not used (Module 1). InputReader wraps both and exposes the result as public fields, three kinds per button:

A level (ButtonA) is true for as long as the button is held. A down edge (ButtonADown) is true on exactly one frame, when it goes down, and an up edge (ButtonAUp) on the frame it comes up. The file also carries ButtonB, ButtonX, ButtonY, both grips, both triggers and both stick clicks, each with the same three fields, plus rightJoystick and leftJoystick as Vector2s (x is left–right, y is up–down).

Finding the controllers

Every frame, the reader asks the XR subsystem for devices that are both a controller and right-handed. The comment records a real regression. The query used to ask for "Right" alone and then required exactly one match. When hand tracking was switched on, a tracked right hand also counted as "Right", the count went to 2, and every right-hand input silently stopped working. Filtering on Controller and accepting >= 1 fixed both halves. The left hand repeats the same query at line 339.

Analogue values, and what is not read

Look at what this block reads. It reads the stick axes, the grip's analogue value, and the trigger as a button (triggerButton). It never reads the trigger's analogue value (CommonUsages.trigger). So on a headset RightMainTriggerValue and LeftMainTriggerValue stay at 0; only the keyboard fallback ever sets them. That hurts nobody today: no script outside InputReader reads any …TriggerValue or …GripValue. But anyone building a half-squeeze feature on those fields would find it working in the Editor and dead in the headset.

Reading input correctly

  • A one-shot action reads the down edge. X opening the menu reads ButtonXDown.
  • A press that acts on release reads both edges. The panel toolkit records the key under the beam on RightMainTriggerDown and acts on RightMainTriggerUp, only if the beam is still on it (Module 5).
  • A held gesture reads levels, every frame. WorldGrab starts on LeftGrip && RightGrip (Module 13). Two grips almost never go down on the same frame, so a test on both …Down flags would almost never be true.
  • Stand down on a single grip. Every game's selection script backs off while either grip is merely held, because squeezing one grip is how a two-grip grab begins, and a live selection beam in that moment misfires.

Frame order

InputReader declares no [DefaultExecutionOrder], so it runs at the default order 0. Everything that consumes input carefully runs later (WorldGrab at 20, the selection scripts at 25) and sees this frame's values. A consumer that also sits at order 0 may run before the reader and see last frame's values. It still sees every edge exactly once, one frame late, because an edge flag stays set until the reader's next Update.

Canvas for pixels, colliders for presses

The panels are Unity UI (uGUI) drawn on world-space Canvases: Image, TextMeshProUGUI, RectMask2D. They use none of uGUI's input system. There is deliberately no EventSystem-driven input module (OpeningScene still has an EventSystem, and it drives nothing). A ray-driven module would be about 250 lines that nothing else here needs. Instead, everything pressable is a physics collider tagged key, carrying a keyInfo with a string name, and the laser pointer reports which one it is touching. If a future feature genuinely needs a Button, text-field focus or a Dropdown, that is the moment to write the module.

Trigger callbacks need a Rigidbody on one side, and they track a single target with no sense of which is nearer. Both are fine for keys, which carry a kinematic Rigidbody, and hopeless for a board. A raycast has neither limitation, but it cannot see BASH's pieces: they are triggers, and the beam ignores triggers (below). So each system is used where it works.

Entering a key lights it (ChangeToOnMaterial), records it as currentKey, and stretches the visible beam to it. GetChild(0) is Visible Pointer and GetChild(0).GetChild(0) is its Dot, both addressed by position. Leaving is where a real bug lived:

Now the board-targeting ray. Read it for three decisions: syncing physics first, starting the ray where the beam is drawn, and ignoring triggers:

  • Physics.SyncTransforms(). Unity normally pushes moved transforms into the physics engine only at FixedUpdate. This project switches automatic syncing off, and RoomContent moves the whole board during Update at order 15. Without the explicit sync, the ray would hit where the board was at the last physics step.
  • The fallback. An exact ray is tried first, so careful aim wins. A 1 cm SphereCast is the backup, because at the smallest board scale a piece is about a one-degree target.
  • Layers. The beam's own Visible Pointer and Dot sit on layer 2, Ignore Raycast, which Physics.DefaultRaycastLayers already excludes. That protects this ray and every other one in the project with no code at all.

Finally, DrawBeam sets the visible beam's length absolutely every frame, to whichever is nearest: the hit, the current key, or 2 m. That also overwrites pointerControl.OnTriggerStay's beam arithmetic, which multiplies the previous scale by itself and drifts while you hover.

meshRenderer.material is Unity's instantiating accessor: it clones the material the first time it is touched. That is harmless on a dozen menu keys, and it is exactly why the games do not use keyInfo to highlight their boards (Modules 18 and 20). growOnPress scales a key up 20% while pressed. It is on for 3D keys and off for rows: a 1160-unit row grown by 20% pushes 116 units off each side into the mask and 19 units over its neighbour.

ScrollList: recycling is a correctness property

When the list is built, EnsureSlots clones the inactive row template once per visible slot. It positions each slot by anchoredPosition, never under a LayoutGroup, because keyInfo.MakeBigger multiplies localScale and a layout group would fight it every frame. It also resizes each slot's BoxCollider from the viewport's width: a collider does not follow its RectTransform, and the authored one was hard-coded to one panel's width. Breaks silently

A list whose row count can exceed its visibleRows must have scrollUp, scrollDown and counter assigned. The room menu's Actions list shipped with none of them, two slots, and three to five rows. Voice Chat and every game action were unreachable except by a joystick push that nothing on screen suggested (UIBugFixes.md §3). Also, never use "ScrollUp" or "ScrollDown" as a row id: the list swallows them before the panel sees them.

CodePad

The 40-key lobby keyboard is gone. It was replaced by a 6 × 6 pad of A–Z 0–9, plus Back, Clear, Close and a submit key, all cloned from one inactive template in Build(). It exists for two jobs, a six-character join code and a username, and the submit key's name changes with the job (Join, for instance). The owner forwards its panel's KeyPressed to HandleKey:

Any other one-character key is appended, up to the maximum length. Submitted(null) means the player cancelled. Two design notes from the file's comments. First, the alphabet is deliberately wider than Relay's join-code alphabet: a key that never appears in a code is invisible, while a code containing a character the pad cannot type would be unjoinable with no error. Second, the cancel key is named Close because CancelKey is both the key's name and its label, and "Cancel" at 44 pt measured 137 units on a 132-unit key. It wrapped, and the key read "Cance".

Conventions the whole toolkit keeps

  • 1 UI unit = 1 mm. Every Canvas is at localScale 0.001. A 1.2 m × 0.9 m panel is sizeDelta (1200, 900), and an 84-unit row pitch is 8.4 cm, legible at 1.6 m.
  • One type scale, in the same units: header 44, status and detail 26, caption 22, row title 32, subtitle 24, state 28. Every surface is one sprite, Assets/Textures/Ui/RoundedRect.png, a 48 × 48 nine-slice tinted by colour.
  • A world-space Canvas is read from its −Z side. The reader looks along the Canvas's forward, which is why a billboard sets forward = camera.forward, and why LookAt(camera) famously mirrors text. A panel gets LookRotation(flatForward), plus a yaw that turns a side panel in towards the player. All four panel placements once added a further 180°, which mirrored every glyph and turned the readable side away (UIBugFixes.md §1). If a panel looks wrong, measure it against the nametag, which has always been right.
  • Row geometry is anchored to the row's edges. Thumbnail, title and subtitle anchor left and the state cell anchors right, so a row survives a panel of another width (CodePad.prefab is 1000 wide against Panel.prefab's 1200). They were once authored as offsets from the centre while anchored left, which put all of them 580 units off the viewport, where the mask ate them (§2).

The payload is hand-encoded, and decoded defensively

The layout is [byte version][ulong mask][ushort len][utf8 name][ushort len][utf8 build]. Decoding is the one place in the project that parses bytes a stranger chose:

Why not JSON? It is three fields on the most fragile path in the project. RoomDirectory: a noticeboard over Relay

Why not Unity's newer Sessions API, which bundles Lobby and Relay? Because it would replace RelayVivox wholesale: the connectInFlight latch, the 15 s watchdog, the dtls match and the shutdown-before-retry fix. That would re-open every networking problem this project has already solved, in new code. Four rules of the Lobby service decide whether the directory works, and the code is shaped by each:

1. Heartbeat, or the room vanishes

Lobby deletes a listing about 30 s after its last ping, and RoomDirectory pings every 15 s. That timeout is a feature: a host that crashes cannot leave a ghost room in the browser for ever. UnpublishAsync exists for a graceful exit, but the timeout is the backstop for every exit that never reaches it, which is most of them. The coroutine keeps running after the host has left the lobby for a game only because RoomDirectory sits on the persistent Network Manager.

2. Rate limits are tight

Roughly: one query per second, five updates per five seconds, and two creates per six seconds, per lobby. So refresh is throttled (CanQuery checks a 1.2 s cooldown and that no query is in flight), and the player count is written by the host only, at most once every ~6 s:

Connect and disconnect callbacks only mark the count dirty; Update sends at most one update per window. The alternative, having every joiner also join the Lobby so that the service tracks AvailableSlots itself, would double the heartbeat traffic and the failure surface for the sake of one number. For the same reason, the browser trusts the host's published players value over AvailableSlots, which only moves when someone joins the Lobby, and here only the host ever does.

3. Publish the build, and grey out what you cannot join

PublishAsync writes the join code, the game key and Application.version as indexed public data on the lobby. Each browsed row then compares that build with its own:

The code comment calls this the highest-value line in the feature. Rooms you cannot join are marked rather than hidden: hiding them would leave a player who has not bought anything staring at an empty browser with no idea why.

4. Degrade, do not block

Any failed Lobby call runs Fail(message, e): Available = false, and LastError is set. The Play panel then greys both public rows as Unavailable, and private rooms keep working. One prerequisite is not code at all: Lobby must be enabled for this project in the Unity Cloud dashboard, as Relay and Vivox already are.

The owner sends; everyone else smooths

At order 20, PlayerControls runs after BoardAnchor (10) has aligned the rig this frame. At the default order, every pose it broadcast would be one frame stale in the shared frame: about 13 ms at 72 Hz, on top of network latency. The owner's half:

  • The root goes on the floor under the head. With a Floor tracking origin the rig's y is the real floor. The old code also subtracted a fixed 1.36 m eye height, which double-counted and left avatars floating about 0.3 m up.
  • The head is sent 0.36 m below the eyes (FaceBelowEyes, the face mesh's pivot offset). The same constant recovers the eye point on the other end, so it exists once.
  • The hands are sent exactly as tracked. The visual offset of the cones lives in the prefab. An old +0.2 * forward nudge left an 18 cm lever arm, so rotating a wrist swept the remote cone through an arc.

Now the other side of every one of those values:

  • Frame-rate-independent smoothing. t = 1 − e^(−Δt/τ) with τ = 0.06 s converges at the same real-time rate whether the headset renders at 72 or 90 Hz. Values arrive at the 30 Hz tick, so assigning them raw makes the cones step. This hides the steps; it does not remove latency. RoomContent smooths the board the same way (Module 13).
  • Snap first, then glide. A newly spawned player jumps straight to its first pose (remotePrimed) instead of sliding in from the origin.
  • One smoothed value feeds two things. The head and the nametag both come from smoothFacePos, so they cannot drift apart.
  • The nametag sits on the head, not above the floor. It is placed at eye point + 0.28 m (NameTagAboveEyes), which has to clear a real head seen through passthrough. The billboard is LookRotation(-lookDirection): forward points from the camera to the tag, the −Z reading rule from Module 5. The labels under TagsRoot keep their authored offsets. When TagsRoot was created in the Editor, Unity's world-position-preserving reparent left every label 6.5 m away (bugFixes2.md §2).

Names, room ownership, and two RPCs that trust their caller

playerName is a FixedString32Bytes, which holds 29 bytes of UTF-8. An over-long value throws on the server and takes the name down for everybody, so names are clamped. But look at what Clamp measures: name.Length counts UTF-16 characters, not UTF-8 bytes. A 20-character name in Cyrillic or Greek, at two bytes a letter, is 40 bytes and passes the clamp. The payload's own 128-byte cap does not help either. This matters more now that names come from IEntitlementService.DisplayName, which on a store build is the player's Meta name, with no length limit.

Hold these two up against the house rules from Module 2. Both allow any client to call them (RequireOwnership = false), and neither checks who called. A modified client could rename another player, or mark itself room owner. roomOwner is what MenuControl uses to grey Place Anchor, and BoardAnchor.RequestPlaceAnchor checks it too, on the placing client. RoomAnchor.PublishAnchorServerRpc checks nothing at all. The one owner-only rule actually enforced on the server is voice (SetVoiceEnabledServerRpc compares the sender with the host's id). Among honest clients all of this is fine: it is the same category as the library gate, a rule nobody can enforce without a trusted server. But it is a gap worth knowing about, and cheap to close (see Try it).

The idea

Every headset tracks the world from its own origin: wherever it happened to start, facing whichever way it faced. Two headsets in one room therefore disagree about where (0, 0, 0) is. Colocation fixes that once for everything:

  1. The room owner presses Place Anchor. BoardAnchor creates an OVRSpatialAnchor (a point in the real room that the Meta runtime can find again) at the owner's feet. It localises it, saves it, and shares it into a fresh group GUID.
  2. It publishes (group, uuid) onto RoomAnchor's server-written variables.
  3. Every other client downloads that exact anchor, localises it, and binds to it.
  4. From then on, each client moves its own rig every frame so the anchor lands on the world origin.

The anchor does not have to be where the board is. The board is placed separately, with the networked two-grip grab (Module 13). So the anchor only needs to be a stable point everyone agrees on: feet, not table, with nothing to aim at and nothing to measure.

Placing it (the room owner)

RequestPlaceAnchor refuses unless four things hold: the Meta runtime is available, a session exists, the local player is the room owner (a client-side check, see Module 11), and no placement is already in flight. Then:

  • The pose is the head's horizontal position at the rig's floor height, with yaw only.
  • The order is strict: set the pose, then add the component, which captures the pose in its Start; then create, localise, save, share. Skipping the save is the most common cause of an unhelpful share failure.
  • The OS setting. Share Point Cloud Data must be on in each headset's privacy settings.

The anchor's GameObject is DontDestroyOnLoad, so a game switch does not throw away seconds of localisation. On success, the owner publishes through RoomAnchor.PublishAnchorServerRpc(group, uuid) and adopts the anchor locally, straight away, without waiting for its own publish to come back.

The arithmetic, in plain words

The anchor's world pose moves with the rig, because the anchor is tracked in the rig's space. Rotating and translating the rig by a transform D therefore moves the anchor by the same D. The code picks the D that sends the anchor to the origin, facing +Z:

  • deltaRot is the inverse of the anchor's yaw.
  • deltaPos = -(deltaRot · anchor.position).
  • Apply both to the rig: rig' = deltaRot · rig + deltaPos.
  • Check: the anchor ends up at deltaRot · anchor + deltaPos = 0.

On a frame where nothing moved, the anchor is already at the origin and D is the identity, which is why the method can safely run every frame. Because deltaRot is yaw-only, the y component of deltaPos is exactly -anchor.y. The rig drops or rises so the anchor sits at y = 0, which is how each headset's floor estimate gets corrected onto the shared one.

The two guards

  • Floor mode first. Until XROrigin reports Floor, Camera Offset still carries its serialized 1.36 m, and every pose here is wrong by that much, so the frame is skipped with a rate-limited warning.
  • The 0.6 m height bound rejects the whole frame rather than half-applying it. It was 0.25 m, which rejected exactly the case the height correction exists for. A headset that has never run Space Setup can be half a metre out, and the check re-ran and re-failed every frame, so such a headset never aligned at all. The startup race the tight bound was really guarding against is now caught directly, by the Floor-mode check.

Capture and Drive: keeping the board under your hands

The capture records a baseline: the midpoint between the hands, their distance apart, the hand-axis yaw, and the board's pose at that moment. Every frame in Holding, Drive computes the board's pose from that baseline and the hands' current position:

There are three ideas in Drive, and each replaced a bug:

  1. The turn is accumulated from per-frame deltas. atan2 wraps at ±180°, so handYaw − startHandYaw would jump by 360° the moment the hand axis crossed that seam, spinning the board a full turn and capping any rotation at half a revolution. Mathf.DeltaAngle of two neighbouring frames is always small. A frame where the hands are stacked vertically (within 1 cm horizontally) has no usable axis, so it contributes nothing: the turn pauses instead of spinning.
  2. Scale is the clamped span ratio, and the clamped ratio drives the position. Bounds are RoomAnchor.MinScale/MaxScale (0.15–4), also enforced by the server. If the position used the raw ratio after the scale hit its limit, the board would stop growing but keep moving, sliding out from under your hands. Hands closer than MinSpan (8 cm) at the start freeze the scale, because there a 1 cm wobble would be a 20% change.
  3. The pose is a similarity transform. pos = center + turn · (applied · (startPos − startCenter)) takes the vector from your hands to the board's origin, scales it and rotates it, then re-attaches it to your hands' current midpoint. Example: the board's origin starts 0.5 m to the right of your hands, and you spread your hands to double the span without turning. The origin moves to 1.0 m to the right: the board grows about the point between your hands, like stretching real cloth. The naive startPos + (center − startCenter) only translates, so any turn or scale would swing the board around its own origin, away from your hands.

The holder applies the result locally every frame, so its hands never lag, and sends it at SendHz (20). Going higher is pointless with a 30 Hz tick and RoomContent's filter.

The naive formula only follows the hands' translation. As soon as the gesture includes a turn or a resize, it would rotate and scale the board about the board's own origin. That origin is never exactly between the player's hands, so the board would swing or slide away from them. The similarity transform takes the offset from the hands' starting midpoint to the board's origin, scales it by the applied factor, rotates it by the accumulated turn, and adds it to the hands' current midpoint. The point between the hands stays fixed relative to the board, as if you were holding the board itself.

Why order matters here

Unity calls every component's Update once per frame, in an order it does not define, unless a class declares [DefaultExecutionOrder(n)]. Lower numbers run first, and unmarked components run at 0. In most games that barely matters. Here, several components move things every frame: the rig onto the anchor, and World Root onto the room's placement. Others measure those same things: they send hand poses, cast the pointer ray, and turn labels to face you. Measuring before moving yields last frame's answer. That is about 13 ms stale at 72 Hz: a highlight that trails a moving board, or a cone a frame behind the hand. Such bugs are invisible while nothing moves, which is why they survive.

Two traps that ordering alone does not fix

  • Physics does not see this frame's moves. Automatic transform syncing is off in this project. Unity only pushes moved transforms into the physics engine at the physics step, but RoomContent moves the whole board during Update. So any raycast or overlap test that must see the board where it is now calls Physics.SyncTransforms() first. PointerBeam does, and so does BASH's blast check (Module 22).
  • Trigger callbacks do not run in frame order. OnTriggerEnter and its siblings fire on the physics step (every 0.02 s), not in Update order. A fast-moving collider can cross something thin between two steps without a callback. That is why BASH sweeps each new line segment with a raycast in the frame it is drawn (Module 22).

Choosing an order for a new component

  1. Does it move the rig or World Root? Then it is a writer. Put it after what it depends on and before every reader, for example between 15 and 20, and make it idempotent if it runs every frame.
  2. Does it use PointerBeam.Hit? Run at 25, after the beam. Never cast a second ray for the same purpose.
  3. Does it read head or hand poses to send or compare? Run at 20 or later.
  4. Does it only need to face the camera or follow the final pose? Do that part in LateUpdate, which runs after every Update.
  5. Does it derive tables that others read? Bake at −10, behind an idempotent EnsureBaked().
  6. None of these? Leave it unmarked. And whatever you choose, update the execution-order table in Assets/Scripts/CLAUDE.md in the same commit.

Checking C# without opening the Editor

The game

Each player has a pawn and a supply of 40 tiles. The rules, from docs/stepsRules.md, as implemented:

  • Setup. Drop your pawn on any empty square: bare board, with no pawn on it.
  • Move. Step to any of the 8 neighbouring squares, but only exactly one level up or down. Momentum: once your first step of a turn goes up, every step that turn goes up, and likewise down. You may never step onto the opponent's pawn, or climb onto their tiles.
  • Capture. Drop exactly one level down onto the opponent's tiles, and you take the whole stack. Your pawn lands on the cleared square, and your turn ends with no build.
  • Build. If you did not capture, press End Turn, then place as many tiles as spaces you moved, at least one and no more than your supply holds. You may build on empty squares or on your own tiles, including under your own pawn, but never under the opponent's pawn.
  • Win. Capture 12 tiles, or have captured more when a supply runs out. Equal counts at that point is a draw.

Two things are deliberate departures from the printed rules, not bugs. There is no turn order: each seat runs its own Setup → Move → Build cycle at its own pace, so a quick player can take three turns while the other thinks, and one player can play alone. And a placed tile can be lifted and re-laid, to fix a misplacement (Module 18).

No prediction, two safe races

The client predicts nothing: it sends the request and waits for the state to change. Because the seats are independent, two new races exist, and both are safe by construction. If both players try to build on the same square in the same tick, the server processes one request first, re-runs IsLegalBuild for the second, and refuses it. The loser keeps the tile and still owes it.

Seats: keyed to ring slots, never given back

Every 4 Hz the server's Update calls ServeSeats, which gives the two seats to the first two players it finds with a ring slot. It polls rather than using a connect callback because spawnSlot is assigned later, when the avatar spawns (Module 11). Each player is seated on their own side if possible:

Seat 0's console is on the board's −Z edge and seat 1's on +Z. The first two players get ring slots 0 and 6, which are exactly −Z and +Z, so ordinarily each player's console is right in front of them. A seat is keyed to a ring slot, not a client id, and it is never released: not on disconnect, not on New Game. The idea is that a player who drops out and rejoins gets their ring slot back and walks straight into their half-finished game. Meanwhile a third person in the room spectates, even while a seat's player is away.

When "you get your slot back" is not true

That design assumes PickFreeSlot hands a returning player the slot they vacated. With two players it always does. Remove the player at slot 6 from {0, 6}, and the widest gap's middle is 6 again. With a spectator in the room it can fail. Players at 0, 6 and 3; the one at 6 drops. From {0, 3}, the widest stretch is 3 → 12, and its middle is 7. The returning player stands at 7, their seat still belongs to slot 6, and both seats count as occupied, so they spectate their own game. Nobody can finish it without New Game, and even that keeps the seating. The same assumption appears in Chasms' "a reconnect gets their army back". Worth knowing before you promise it to players.

The grid: measured from the scene, not typed in

Nothing in StairsGame.unity carries a cell number. StairsBoard.Bake reads World Root > Board > Cells, sorts the eight rows by z, and sorts each row's cells by x:

  • Sibling order is not grid order. The eight cells in every row are named Cube, Cube (4), Cube (1), Cube (5), Cube (2), Cube (6), Cube (3), Cube (7), and they sit in that order in the Hierarchy. Reading GetChild(i) as column i would give a shuffled board that still looks plausible in play. Chasms does the opposite, and uses sibling order as its plateau numbers. The two boards were authored differently, and each file's approach is right for its own board.
  • Everything is measured in Stairs Root's local space. So the grab can move, turn and resize the board all game and nothing is ever re-baked. Stairs Root is deliberately not under Board, which is scaled (2, 0.02, 2); a child of it would be squashed with it.
  • The top of a cell comes from Renderer.localBounds, pushed through the cell's own transform. Renderer.bounds is a world-space box that grows the moment the board is turned.
  • The bake is idempotent (EnsureBaked) and runs at order −10, because a server tick can arrive in the same frame the scene loads.

A bare square is found from where the ray landed, not from what it hit: the point is rounded to the nearest grid position. Rounding snaps the 1 cm gaps between cells to the nearer cell, so a drag never dies in the cracks, and anything past the outer row rounds out of range. Cell 0 is the corner nearest seat 0 (−X, −Z), and cell 63 is the far corner. Index(row, col) = row × 8 + col. Neighbours fills a caller's buffer with the 3, 5 or 8 adjacent cells, with no allocation. Select World Root > Stairs Root in the Scene view to see a gizmo line snaking from cell 0 to cell 63 in index order; a mis-sorted grid shows up at a glance.

Lifecycle, and New Game

StairsGame sits on an in-scene object, so it lives and dies with StairsGame.unity. On spawn, the server calls ResetGame, which keeps whoever is seated and clears everything else. Everyone then subscribes to the lists and raises BoardChanged once by hand, since a late joiner's initial list contents raise no events (Module 2). ResetGame is also the one place allowed to Clear() and refill the lists; every other write is a single element. Switching to another game and back therefore deals a new game, intentionally, which is why OnGameSelected does nothing, and New Game is its own room-menu action (RequestResetServerRpc, callable by any player).

The ghost

Three details keep the ghost honest:

  • It sits on the ray that positions it. StairsView.CreateGhost disables and destroys every collider on the clone, and puts every one of its objects on the Ignore Raycast layer. Left solid, the ghost would sit in front of the board and freeze the drag the moment it started. The layer is what really protects the ray, because Destroy only takes effect at the end of the frame.
  • A lifted tile is hidden locally only (SetLiftedCell). The server still has it on the tower, and the drag may be abandoned. ReconcileTower re-applies the hide on every rebuild, because an opponent's build anywhere marks the whole board dirty and would otherwise put the tile back under the player's hand.
  • The state still counts the lifted tile, so over its own square the ghost would float one tile too high. MoveGhost subtracts a thickness there. Off the grid, the ghost rides on the end of the beam, so it visibly remains in hand.

Re-laying a placed tile is the one affordance not in the printed rules. It exists to fix a misplacement and is deliberately narrow: your own tiles, the top of the stack, never under a pawn, and free, with no supply spent and no tile owed. Where it may land is plain IsLegalBuild, so "one owner per tower" still holds.

Highlighting with StairsTint

Legal destinations light green, a capture red, the selected pawn yellow, and whatever the pointer rests on white. The hover is applied last, so pointing at one of several lit squares shows which one the trigger would take. Highlights use a MaterialPropertyBlock, never keyInfo's material swap:

  • A property block overrides a colour per renderer without creating a material instance. renderer.material would instantiate one per object: 64 leaked instances on a board of cells, on a mobile GPU rendering in stereo.
  • A tint blends with what is there (Lerp from the authored colour), so a highlighted step still shows whose it is.
  • Clearing sets the block to null rather than writing the original colour back. That lets the renderer rejoin URP's SRP batcher.
  • One block is reused, never allocated per call, and TextMeshPro renderers are skipped, since their colour is a vertex colour.

StairsTint is a deliberate second copy of Chasms' PlateauTint, not shared code. The Stairs assembly cannot see Plateau's, which is the whole point of the boundary. Moving the component into Shared would mean editing Chasms. Stairs also needs only the leaner half, because its seat colours are already authored materials.

Known rough edges

  • A committed re-lay flickers. The drag ends in the same frame the request is sent, so the hidden source tile reappears for the round trip until the new state removes it. That is the no-prediction rule working as intended.
  • A game in progress is lost on a scene switch, because the state is in the scene (Module 17).
  • Spectators are untested. The code handles them (LocalSeat() returns NoSeat and selection stands down), but nobody has tried a third player.
  • There is no way to concede, so a game against an absent seat never ends.

The game, and how much of it exists

In docs/plateauRules.md, players move troops, parshendi and shardbearers across a field of plateaus. They connect plateaus by laying bridges over the "faint lines" between them, and they collect gemhearts. What the code implements is the first slice. Starting forces: 2 bridges, 6 troops, 2 parshendi and 1 shardbearer each, all on the central plateau. And where each piece may move. Turns, harvesting, buying and winning are not implemented: anyone may move their own pieces at any time. Players act out the rest by agreement, helped by a sandbox spawn menu (Module 20). The rules document says 40 plateaus; the scene has 41. The code counts the scene's children, so the document is the stale one.

There are six piece kinds (PieceKind): Bridge 0, Troop 1, Parshendi 2, Shardbearer 3, Gemheart 4, Chasmfiend 5. The numbers travel on the wire, so new kinds can be added at the end but existing ones are never renumbered. The last two are neutral: they belong to PlateauConst.NeutralSeat (255) rather than to a player.

A piece is a stack

Four players start the game with 16 stacks between them. Here, unlike Stairs, a seat is the ring slot (spawnSlot), so up to 12 players can play; and the seat is also the colour index (PlateauPalette, Module 20). Two more structs complete the state. BridgeEdge is one "faint line", stored with a < b so an unordered pair has one representation. PlacedBridge is (edge, seat): a bridge laid across a gap. A bridge still in reserve is simply a PieceStack of kind Bridge sitting on a plateau.

Where the state lives: on the persistent Room Anchor

PlateauGame is a second NetworkBehaviour on Room Anchor.prefab, beside RoomAnchor. That object is already spawned exactly once and already survives every game switch, and it already holds "the room-wide facts about a session". A new network prefab of its own would have changed the global prefab list that every build must agree on (Module 16). The consequences show up throughout this game:

  • The board survives a switch. Leave Chasms and come back, and the pieces are still there. That is why picking Chasms always resets the board (Module 6), even from inside Chasms: there is no other moment to clear it.
  • PlateauGame exists in every scene, so its own tick must check that Chasms is actually loaded before doing anything.
  • Its session is always registered, which is how Stairs can reach OnGameSelected, and why GameSessionRegistry.Active resolves through the catalog rather than taking the last registration.

The replicated state is four NetworkLists: stacks, edges, placedBridges and gemheartScores. There are also server-written variables for boardEpoch, plateauCount, graphHash and boardLive, plus the four chooser values from Module 20. Lists are mutated in place: a move is two small list changes, about 16 bytes, where clearing and refilling would resend the whole board.

The board graph, measured from geometry

Nothing in the scene says which plateaus connect. There are no ids, no neighbour lists and no data asset. ChasmGame holds 41 Plateau instances under Plateaus and 81 Bridge Spots instances under Bridges, and each bar is one of the rules' faint lines. So PlateauBoard works the graph out from their positions at load. Doing this at runtime, rather than baking it into an asset once, suits a board that is still being hand-edited: no bake step can be forgotten.

  • A plateau's index is its sibling order under Plateaus. Reordering those children renumbers the whole board, and the numbers travel on the wire. Adding one at the end is safe. This is the opposite of Stairs, which sorts by position.
  • A plateau's centre and radii come from renderer localBounds, not from its transform. The prefab's mesh sits on a nested child that is offset and rotated 180°, so the root's position is nowhere near the centre.
  • The start plateau is found by name. It must be called Central Plateau, exactly. Without it the bridge rules have no seed, and the code falls back to the largest plateau with an error.
  • Everything is measured in World Root's local space, so nothing is re-derived when the board is grabbed.

The rest of BakeEdges handles the awkward cases:

  • Both ends pick the same plateau (a short bar lying mostly over one). The end that fits better keeps it, and the other end takes its runner-up.
  • An end more than two radii from anything (MaxEndpointScore, 4 in squared units) is rejected and reported.
  • Pairs may have two bars. Up to two bars on the same pair of plateaus become separate edges (MaxEdgesPerPair). The six exits around the central plateau were re-authored on top of the originals, and both bars of each pair are kept, so two bridges can occupy that connection at once. A third bar would collapse.

The server publishes the edges, and clients use that copy

Every client derives the same graph from the same scene, so why send it? Because the derivation turns floating-point geometry into integer indices through an argmin. An Editor host on x64 and a Quest on ARM64 could break a near-tie differently. Then one of them would highlight destinations the other refuses for ever, with no error anywhere. So the server publishes its list, 162 bytes, and the rules on every client use that copy:

Geometry stays local, where a sub-millimetre disagreement is invisible. An FNV-1a hash over the edge list (graphHash) catches a client whose own bake disagrees, which means a different scene or build: SyncMirror logs it once as an error. Edge indices travel as bytes, and 255 means "none", so the board is capped at 255 edges. A Debug.Assert names that failure in advance, the day someone draws the 256th bar.

Movement as graph search

PlateauMoveRules is the one place the movement rules are written. The client runs it to decide what to light, and the server runs the same call to decide what to allow. So a client can never light a plateau the server will refuse, and a modified client cannot talk the server into a move. The "budgets" come from the rules:

Where can a piece get to, spending at most that budget? That is a breadth-first search over states, not plateaus: a state is (plateau, bridges spent, jumps spent). 41 plateaus × 3 × 2 is 246 states, cheap enough to redo on every selection:

  • One integer encodes a state: (p × bridgeStates + b) × jumpStates + j. Unpacking it takes three divisions.
  • Two ways to leave a plateau along each edge. Cross it if the edge holds one of this player's bridges, spending one bridge step (an unlimited budget stays in state 0 for ever). Or jump it if a jump remains, bridge or not.
  • No garbage. The scratch buffers are static and reused, so running it on every selection allocates nothing.

A consequence players notice: at the start, troops have no legal destinations, because nobody has laid a bridge yet. That is the rules working, which is why a selected troop with nowhere to go shows its count in red instead of silently doing nothing. Parshendi and shardbearers can jump to the six plateaus around the centre. The file header lists the readings taken where the rules are ambiguous: "bridges" means your own; "two bridges" means up to two; the jump can come at any point in the move.

Bridges: a gap, not a destination

A bridge is placed into a gap. The rule says it must go from "a plateau already connected by that player's bridges" to a new plateau. Every bridge question reduces to one predicate:

In words: the gap must be empty, since one bridge fits per gap whoever owns it. Exactly one end must be inside "the connected system", with the other outside ("to a new plateau"). The one exception is the free twin bar of a pair this player has already bridged. The component is the set of plateaus reachable over this player's bridges, and which plateau it grows from is the key decision:

  • Placing from reserve seeds from the central plateau. With no bridges down, nothing is "already connected", so without this seed no first bridge could ever be placed, and the game would deadlock on turn one.
  • Re-laying a bridge already on the board seeds from that bridge's own two ends: a bridge is local to the plateau system it is touching. Seeding both ends makes the bridge's far side count. It also stops a bridge in a detached piece of the network from being teleported back to the part that reaches the centre (docs/bridgeMovementUpdate.md).

View.movingEdge is the single switch between the two, and it does not lift the bridge out of the graph: its gap stays occupied. View is a struct, so a default movingEdge would be 0, a valid edge meaning "edge 0 is in hand". That is why there is exactly one place views are built, PlateauGame.TryBuildView, and it always sets the field.

The bridge RPCs carry an edge index, not a destination plateau. A plateau can be reachable through two different free bars, and a server that re-derived "which bar" from a plateau could pick the one the player did not click. So the client resolves the gap, from the bar it hit or by TryResolveBridgeEdge, and the server re-checks that exact gap with IsLegalBridgeEdge, the same predicate the highlight used.

The server: validate everything, then mutate

All ten ServerRpcs on PlateauGame follow this shape:

  1. Refuse the wrong kind. Bridges have their own RPCs.
  2. Check the epoch. The client sends the boardEpoch it saw when it armed the move, so a request sent across a reset is dropped.
  3. Find the seat from the sender. The sender id maps to a seat (their ring slot); the message never names a seat.
  4. Bounds-check every index.
  5. Check ownership. FindStack(from, seat, kind) only finds the sender's own stack.
  6. Re-run the rule through PlateauMoveRules.
  7. Clamp the count, then mutate in place.

The neutral-piece RPCs use NeutralSeat as the owner, but still require a seated sender. There is no local prediction: the client waits for the lists to change.

One tick at 4 Hz does everything else

Because the state rides on the persistent anchor, the tick first checks that Chasms is the active game. GrantMissingArmies gives starting forces to any seat that has no pieces at all. One rule covers three situations: the first entry into Chasms, the moment after a reset (everyone is missing an army), and a late joiner. A player who leaves keeps their pieces, so a reconnect that lands on the same ring slot gets their army back. That is subject to the ring-slot caveat from Module 17; and a different person taking a vacated seat inherits that army. When a scene load completes, nextTick is set to 0, so the board appears the next frame instead of up to a quarter second later.

The interesting part is how a two-second animation coexists with an authoritative server. Counters rather than watching the result values directly, because a spin can land on the same answer as last time, and a NetworkVariable set to the value it already holds tells nobody anything (Module 2).

It is called on binding as well as on a result, because a client that joins later gets the current values with no change event. The flourish also does not try to land exactly when the server resolves: it keeps shuffling slowly until the answer arrives, because a flourish still visibly thinking reads better than one that freezes early on a guess. Explain how a bridge move travels from the player's click to the server, and why the client resolves the gap rather than the server.

Show model answer

While a bridge is selected, every candidate gap's bar is faintly tinted. The game

Four players sit around a 3 m square of water with four islands in it. Each owns a base carrying four gamepieces: boat (0), plane (1), sub (2), helicopter (3). Point at one of yours and pull the right trigger to select it; what happens next depends on which piece it is. The four split into halves two different ways, and the two predicates sit one line apart on purpose:

IsSurfaceCraft: an island kills it✔✔

A piece's kind is its sibling index under its base, and that integer already travels in every selection RPC. The four pads sit at child index n + 4. Like the other two games, BASH is not turn-based here: anyone may fire at any time, and a "turn" ends when the piece is deselected. The rules' win condition (last undestroyed piece) is not implemented.

Bash Root is the content frame

BASH was written for a static world. Its board sat at world (0, 0.6, 2), and every networked value in it was a plain world-space Vector3. In this project World Root moves, turns and rescales continuously under the two-grip grab, so a world-space value for anything under it goes stale the moment somebody touches the board. The fix is the same one Chasms and Stairs use: measure everything in the content frame's local space. BASH's frame is Bash Root, and every conversion goes through four helpers, so there is one place to look when a shot comes out of the wrong end of a cannon:

Note that the direction helpers normalise. InverseTransformDirection divides by the content scale, so without that a direction would carry the board's scale into every speed. Because the speeds are then board-local units per second, a shot crosses the same fraction of the board however big the players have made it. That falls out of the design rather than being extra work.

Bash Root is a child of Board, not a sibling, so Board's scale is the one knob that resizes water, walls, islands, bases and trails together. Board is authored at scale 1, a true 3 m board, so players standing on the 2 m ring are half a metre clear of the walls. The acceptance test for the whole port is one gesture: grab the board with both grips, move, turn and resize it, then fire. The trail must come out of the cannon and stay on the board.

Seats: a ring slot is not a base index

BASH used to hand out bases by NetworkManager.ConnectedClients.Count, which is wrong in a way that bites quickly: when one player leaves and another joins, the count is the same again and two players get the same base. The port replaced it with PlayerControls.spawnSlot, the project's one stable per-player index. But a ring slot is not a base number:

Read the table: slot 0 → base 0, slot 3 → base 2, slot 6 → base 1, slot 9 → base 3, everything else → no base. Those four entries are a measurement, not a convention: they are the four ring slots where a base actually stands, matching both position and facing, so your base is the one you are standing behind. Seating then happens in two passes, and the order between them is the point:

  • Pass 1 is the rule. A player standing on one of the four base slots gets that base, whoever else is in the room and in whatever order Netcode enumerates clients.
  • Pass 2 is a fallback for a ring fragmented by mid-game departures, where PickFreeSlot can answer 11 for a new joiner. Rather than leave base 0 standing empty while somebody has none, hand out the lowest unclaimed base. Running it after pass 1 is what stops a leftover player taking a base that another player's slot entitles them to. It also keeps a client's existing base rather than re-deriving one each tick, because a base changing hands four times a second would re-run OnGainedOwnership each time.
  • The tick runs at 4 Hz, not on a connect callback, for the identical reason Stairs and Chasms poll: spawnSlot is assigned inside PlayerControls.OnNetworkSpawn, which can run later than the connect callback.
  • A reconnecting player is handed the standing base with ChangeOwnership, not a second one, and NetworkBaseControl.OnGainedOwnership re-wires it to their Controls.

One known cosmetic gap

LocalBaseIndex() derives a player's colour from their ring slot, which is pass 1's logic. A player who got their base from pass 2 answers −1 there, and their trails clamp to colour 0. It is confined to the same five-players-and-a-departure case the fallback exists for. Fixing it properly means the server telling each client which base it was handed, which is not worth a NetworkVariable until spectator seats are tested at all.

Where a piece ends up is an RPC, not a variable

This is the module's most transferable lesson: a message that depends on some other state having arrived first is a message waiting to break. Name what you are acting on. activeRot stays a NetworkVariable because it is derived every frame by every client and is only ever written while a piece is selected. The visible symptom of the old bug is worth remembering too: the trail appeared but the piece stayed put, until its owner selected it again and republished a pose at a moment when something was selected to receive it.

The pose travels board-local and is converted on the way out (BashRoot.ToWorldPoint). The shooter applies it locally first, so its own piece does not wait for the round trip.

Islands, and reset

IslandManager was board-local from the start, so the port changed nothing in it. That was a useful accident: its baseExclusionZones already matched SpawnManager's rebased seat positions exactly, which is what confirmed the rest of the rebasing was right. Random Islands places four islands by rejection sampling: each candidate must fit inside the playable rectangle, keep minSpacing edge-to-edge from the islands already placed, and stay baseExclusionRadius clear of all four bases. After 100 failed attempts it warns and uses the last candidate: it degrades rather than throwing or looping. The server generates the layout, caches it, and broadcasts it; a late joiner asks for the current layout in OnNetworkSpawn, because a ClientRpc sent before it joined is gone.

Reset Game goes through BashRoot.InvokeMenuAction (Module 6) to ControlListener.ResetBoard, and on to NetworkBaseControl.ResetBases: every piece switched back on, moved to its authored pad position, and every object tagged line despawned. Those pad positions are relative to the base, so the port left them alone.

Taking the wall rule away from the physics engine

The second half of every turn is a movement line: a trail that grows while the trigger is held, bends with the joystick, stops on a wall, and carries the piece to its end. It has a MeshCollider, and LineControls.OnTriggerEnter owns the rules. That was not enough:

Work through the arithmetic, because it is the general lesson. Physics runs at 50 Hz; the headset renders at 72–90. The trail accelerates, so late in a shot its tip advances about 0.2 board units per frame against a wall 0.04 thick. A trigger is only evaluated on a physics step. So the tip can be on one side of the wall at one step and well past it at the next, the player can release in between, and EndCannonLine clears checkForCollisions on the way out — so nothing will ever look again. That is a submarine driving through a wall and living.

The fix is not a smaller time step or a thicker wall. It is to evaluate the rule where the geometry is known exactly: one raycast along the one segment just drawn, in the frame it is drawn.

Two passes, and the order between them is the rule, not an optimisation. The first finds the nearest blocker and clamps the segment's end onto it. The second kills only what lies at or before that point — so a piece standing behind the wall the shot stopped at is not killed through it. Collapsing these into one loop would make lethality depend on the order Unity happened to fill the hit array.

Two subtleties that read as accidents and are not:

  • A ray never reports a collider it starts inside. That is what keeps a piece firing from its own pad — tagged obstacle, which always blocks — from dying on the very first segment. The physics engine's own behaviour is carrying a game rule here, so it is written down.
  • RaycastNonAlloc silently stops filling at the array's length. sweepHits is a RaycastHit[16], sized for the colliders one frame of trail can run through rather than for the whole board. A missed wall is the exact bug the sweep exists to remove, so that number is a correctness constraint, not a memory tuning knob.

Committing the shot: order, and one guard

EndCannonLine is where five things have to happen in one order. It opens with a guard that looks like paranoia and is not: a trail entering the corner where two walls meet raises two OnTriggerEnter calls in one frame, so this method can be re-entered, and without the guard the second call indexes an empty list.

  1. Grow one last step, unless something already stopped the trail. trailBlocked is the flag that both detectors set — the trail's own trigger and the sweep — and skipping the final step is what stops the trail growing past the wall it just stopped at.
  2. Read the piece index before deselecting. Deselect() nulls activeGamepiece, so both the move and the kill would silently address nothing.
  3. Publish the trail via SpawnManager.SpawnNetworkCannonLine, so everyone sees where the shot went.
  4. Move the piece (board-local, named in the RPC — Module 21), turn its colliders back on, and deselect.
  5. Kill the shooter's own piece last, only if something stopped the trail. A bad shot costs you the piece, and the wreck is left at the wall it hit.

The local preview is released rather than destroyed here, and that is a deliberate difference from CancelShot. Because step 4 deselects, CancelShot runs on the very next frame of every shot — and if it still held the preview it would take it down before the replicated trail had finished its round trip, producing a visible flicker at the end of every turn.

  • Because activeRot is server-written in that phase

The joystick means three different things across the other phases — turn the parked piece, bend the arc, bend the trail — and deliberately nothing here.

Why does GrowTip raycast each segment itself instead of relying on the trail's MeshCollider and OnTriggerEnter?

  • Mesh colliders cannot raise trigger events
  • To avoid the cost of a mesh collider entirely
  • Because trigger callbacks do not fire for the client that owns the object
  • A trigger is only tested on a 50 Hz physics step, and late in a shot the tip covers ~0.2 board units per frame against a 0.04-thick wall, so a shot can cross a wall between two steps and be released before any step looks at it

And nothing would look afterwards: EndCannonLine clears checkForCollisions on the way out. The trigger path still exists; the sweep makes the rule exact rather than merely likely.

Every Physics query in this file passes QueryTriggerInteraction.Collide. What happens if one is left out?

  • It finds nothing at all, silently — every collider in the BASH scene is a trigger, and the default is Ignore
  • It throws at runtime
  • It finds triggers but not solid colliders
  • Nothing; it is the default

An expensive no-op with no error: the wall rule stops working, or the shell stops killing anybody, with nothing in the console.

GrowTip runs two loops over the same hit array. Why not one?

  • To let Blocks stay pure
  • Because RaycastNonAlloc may return hits out of order and the second loop sorts them
  • The first loop finds the nearest blocker so the second can kill only what lies at or before it — otherwise a piece behind the wall the shot stopped at would die through it
  • One loop would exceed the 16-element array

Collapsing them would make lethality depend on the order Unity happened to fill the array — a bug that reproduces only sometimes.

Two different guards — minArcRange and the sqrMagnitude test at the end of GrowTip — exist for the same underlying reason. What is it, and why is it guarded from outside rather than fixed at the source?

Show model answer

PipeRenderer.GenerateCylinder builds each ring of the tube by rotating the previous one with Quaternion.FromToRotation on the difference between consecutive positions. Two identical consecutive points make that difference the zero vector, and the mesh comes out degenerate or NaN — with no exception and nothing in the console. The arc reaches that state when its range is ~0; the trail reaches it when a blocker sits exactly on the previous tip and clamps the new point back onto it. Both callers therefore refuse to hand PipeRenderer a zero-length segment. It is guarded from outside because PipeRenderer is inherited, uncommented code from the previous application that the port had no other reason to touch; both call sites are one line each, and the trail simply ends one point short of where it was going to end anyway.

In EndCannonLine, why is the piece index read before Deselect(), and why is the shooter's own piece killed last?

Show model answer

Deselect() nulls activeGamepiece, and ActivePieceIndex() answers −1 when that is null. Reading it afterwards would leave both the move RPC and the kill silently addressing nothing — the piece would stay where it was and a fatal shot would cost nothing. The kill comes last so the piece has already been moved to the end of the trail and that move has already been published to every client; the result is a wreck left at the wall it hit, visible to everyone, rather than a piece switched off at its old position or a move that never went out. trailBlocked — set by either detector, the trail's own trigger or the sweep — is what distinguishes "the player let go" from "something stopped it".

Recipe 4 — change a serialized default

Editing public float thing = 0.25f; in a .cs file is not enough on its own, and this has already caused a real bug. A serialized value wins over the field initializer, so every prefab and scene that carries its own copy keeps the old number. The worked example is CameraController2.MaxAnchorHeightDisagreement: raising it in code changed nothing, because PersistentRig.prefab carries its own copy and that is what runs.

Recipe 5 — debug a join that hangs on "Joining room…"

This is the project's single most mystifying failure, and it now has three separate things watching for it. Work down the list:

  1. Read the disconnect reason. NetworkProbe logs connection LOST with NetworkManager.DisconnectReason into the in-headset box. An empty reason is Netcode's config-hash refusal — it sends no reason string at all. GameController reports exactly that as a probable build mismatch.
  2. Compare the two builds. ForceSamePrefabs hashes the registered prefab set, and NetworkConfig — which now includes ConnectionApproval being on — is hashed alongside it. Anything that moved either means an older headset cannot join a newer one. Flash both headsets from the same build, every time. NetworkProbe's heartbeat prints prefabs= for a direct comparison.
  3. Check connectionType matches. RelayVivox.connectionType defaults to dtls and must be identical on host and joiner.
  4. Check the prefab list is clean. DefaultNetworkPrefabs.asset must hold only prefabs under Assets/; a package Editor/ prefab getting in makes Editor↔device connection structurally impossible. NetworkPrefabListGuard turns Netcode's auto-generator off and fails the build if a foreign entry returns.
  5. If it failed after Relay accepted it, the 15 s watchdog has already returned the player to the code pad and called NetworkManager.Shutdown(), so a retry is not refused by an instance still grinding through 60 connect attempts. If you are not seeing that, the watchdog is what to check.

Recipe 6 — debug colocation

  1. Turn ColocationProbe off first. It is m_Enabled: 1 on PersistentRig.prefab — running in every build — and at 1 Hz it refills the ten-line debug box every ten seconds, scrolling away anything else you were reading.

Forty questions

Weighted towards the shared platform, because that is what every game sits on and what breaks three games at once. Pick an answer for each; nothing is revealed until you grade the whole paper. Each explanation links back to the module that covers it.

BASH once called PlateauBoard.FindDescendant. Why can it not do that today?

  • The method was renamed to HierarchyUtils.FindDescendant
  • MRBoardGame.Bash and MRBoardGame.Plateau are separate assemblies and neither references the other, so it is a compile error
  • Plateau's scripts are Editor-only
  • A runtime guard in GameSessionRegistry refuses cross-game calls

The shared helper exists too, but the point is that the boundary turned "discover it in a headset" into "cannot compile". Editing one game recompiles only that assembly.

What makes NetworkVariable write permission the project's security boundary?

  • Server-written values are encrypted on the wire
  • Owner-written values are validated by Netcode against the prefab
  • There is no dedicated server, so anything a client must not be able to forge has to be server-written and changed only through a ServerRpc that validates the sender
  • Read permission decides who can see a value, which is the same thing

The "server" is another player's headset. Owner-written is reserved for things that genuinely are facts about their owner — hand and head poses, BASH's aim.

A client joins a room whose NetworkList already holds twenty entries. What does its view see?

  • The entries replicate, but OnListChanged is not raised for them — so a view that only listens to the callback stays empty
  • Nothing: existing entries are not replicated to late joiners
  • Twenty OnListChanged events, one per entry
  • One OnListChanged event with the whole list as the payload

Same trap as OnValueChanged not firing for the value a client arrives with. Every view here has a "rebuild from current state" method and calls it in OnNetworkSpawn as well as on change.

Why does this project treat static fields as a hazard to reset explicitly?

  • Statics are not thread-safe
  • Netcode cannot replicate static state
  • IL2CPP strips unused statics
  • A static outlives a scene load and a Play session with domain reload off — which is why one public room hosted in the Editor once made every private room after it public

BoardAnchor.Awake resets RoomOptions and the alignment flag for exactly this reason.

What does gameObject.scene.name return on anything under PersistentRig?

  • The name of the scene it was instantiated in
  • The fixed pseudo-scene "DontDestroyOnLoad", for ever — so code telling a game scene from the lobby must read SceneManager.GetActiveScene().name
  • The name of the currently active scene
  • An empty string

CameraController2.PlaceAtRingSlot was the one place that read the old way.

PersistentRig.prefab's root sits at (0, 0, −10), which is wrong for every game board. Why is it left alone?

  • It is overwritten by the prefab variant in each scene
  • The value is unused; the rig is always repositioned on spawn
  • PlaceAtRingSlot repositions the rig at runtime in game scenes only, so the baked pose is what the lobby uses — "fixing" it breaks the lobby instead
  • Because colocated players never use it

Two scenes never call PlaceAtRingSlot: OpeningScene and the legacy GameScene.

InputReader queries devices with Controller | Right rather than bare Right. What went wrong when it did not?

  • A tracked right hand also matched, pushing the match count to two and silently killing all right-hand input
  • The query threw when no controller was connected
  • It matched the headset as well as the controller
  • Bare Right is not a valid characteristic

Enabling hand tracking alongside controllers was all it took. Each hand independently falls back to the keyboard when its controller is absent.

ScrollList recycles a fixed number of row slots. Why is that a correctness property rather than an optimisation?

  • Instantiating rows at runtime would move the join config hash
  • A RectMask2D clips pixels, not colliders — so a tall sliding list leaves rows you cannot see where the beam can still press them
  • Unity limits a Canvas to sixteen children
  • Recycled rows keep their keyInfo state across scrolls

Rows that never leave the viewport have nothing off-screen to press.

Why does a list refuse to scroll while the right trigger is held?

  • The joystick and the trigger share an input axis
  • Scrolling mid-press would cancel the press, and cancelling is the panel's job
  • To keep keyInfo.MakeBigger from fighting the layout
  • A press begun on row 3 and released after a scroll would act on whatever row 3 now shows — the key object is the same, its keyName is not

One if removes the whole class of bug. The other half of the rule: a row's keyName is a stable id, never a slot index.

GameSessionRegistry has two lookups, ForKey and Active. Why is conflating them a bug?

  • ForKey answers "the room is switching to this game" and runs before LoadScene, so it cannot be keyed off the active scene; Active answers "the game on screen now" and resolves through the catalog
  • ForKey is server-only and Active is client-only
  • Active returns the last game to register, which is always correct
  • They differ only in null handling

In BashGame both BashRoot and the still-registered PlateauGame are present, so "last one to register" would be a coin toss.

A client presses a game row. What does the server do with the key it receives?

  • Passes it to LoadScene — the menu only ever builds rows for valid games
  • Compares it against the sender's ownedMask and nothing else
  • Validates it against GameRoutes, then the room's public lock, then the room's combined library, and only then calls NetworkManager.SceneManager.LoadScene
  • Broadcasts it so each client loads the scene itself

Never hand a client string to LoadScene. The menu's own filtering is cosmetic; these three checks are the enforcement, and clients must never call SceneManager.LoadScene during a session.

A room's playable set is the union of every player's library, not the intersection. Why?

  • The intersection is expensive to compute each time the menu opens
  • Somebody who owns a game can show it to the table; requiring everybody to own it makes buying a game pointless until your whole group has
  • Because ownedMask is a bitmask and OR is cheaper than AND
  • The intersection would be empty whenever a spectator joins

It is computed on demand — when the menu opens and when a switch is validated — because both are rare and a cache would need invalidating on spawn, despawn and change.

Why does the code state outright that the library gate is not DRM?

  • Because the store is a mock and no real purchases happen
  • Because paid games are not shipped in the APK until purchased
  • Because Meta's entitlement check runs on the client and can be disabled
  • Because ownedMask comes from the joining client's own approval claim and there is no dedicated server, so a modified client can claim to own everything — it is a UX and social rule

The assets ship in the APK either way, since Meta add-ons gate entitlement and not delivery. Say so rather than building a defence that cannot work.

A connection LOST arrives with an empty DisconnectReason. What does that mean?

  • Netcode's config-hash refusal — ForceSamePrefabs and NetworkConfig differ, so the two devices are on different builds
  • The Relay allocation expired
  • The host called Shutdown()
  • The transport timed out before Netcode's handshake began

It sends no reason string at all, which is why GameController reports exactly this case as a probable build mismatch and the room browser greys such rooms as Different version.

JoinRoom deliberately calls no LoadScene. Why not?

  • The joiner does not know which game the room is playing
  • Loading a scene would drop the Relay allocation
  • Netcode synchronizes the joiner into whatever scene the room already has open
  • Because GameRoutes.DefaultScene is only valid for a host

A host of a private room does open StairsGame; a public room opens straight into the game it is locked to. The joiner follows.

Why does the join watchdog call NetworkManager.Shutdown() before returning the player to the code pad?

  • To release the Vivox channel
  • So a retry is not refused by an instance still grinding through its 60 connect attempts
  • Because ConnectionApproval cannot be changed while a client is connecting
  • To force RoomDirectory to re-publish

The other half is that the failure is now visible at all: Relay accepting the allocation only means the REST call worked, and nothing used to watch the two handshakes after it.

Unity Lobby deletes a lobby after roughly 30 seconds without a heartbeat. Why is that described as a feature?

  • It keeps the project inside the free tier
  • It forces joiners to refresh, which spreads out the rate-limited queries
  • A host that crashes cannot leave a ghost room in the browser for ever — the failure everyone hits when they clean up only on a graceful exit
  • It guarantees the Relay allocation and the lobby expire together

RoomDirectory pings every ~15 s for as long as the room is open. And if Lobby is unreachable, the two public rows go inert with a reason while private rooms keep working: degrade, do not block.

X opens the room menu. What does it do in the lobby?

  • Opens the menu with the games list only
  • Opens the menu and logs a warning about no local player
  • Closes the Library panel
  • Nothing — it is gated on GameRoutes.IsGameScene

It used to resolve no local player, warn, and would now open a list filtered to nothing. OpeningScene does have a MenuControl — it arrives with PersistentRig.

PlayerRing.PickFreeSlot hands out the middle of the widest empty stretch, and never re-spaces players who are already seated. Why not re-space?

  • Teleporting somebody because a third player joined is exactly the involuntary rig move that makes people sick in passthrough
  • Slot indices are on the wire and cannot change
  • Re-spacing would break BASH's BaseForRingSlot table
  • Occupancy is stored in a static that cannot be rewritten

Occupancy is read from live players rather than a static, so a slot cannot leak on an ungraceful disconnect. Nothing about the ring is networked.

Hand poses go on the wire as position plus a Quaternion, not position plus a forward vector. Why?

  • A quaternion is smaller than a Vector3
  • NetworkVariable cannot serialise a bare Vector3
  • Rebuilding a rotation with LookRotation discards roll and is ill-conditioned near vertical — and pointing a controller straight down at a board is the default posture here
  • Because ClientNetworkTransform requires a rotation channel

The same family of mistake as reconstructing a pose from partial information. Remote poses are then smoothed with a frame-rate-independent lerp, and a freshly spawned player snaps rather than gliding in from the origin.

Why is alignment to the room anchor re-applied every frame instead of once on binding?

  • The anchor's UUID can change during a session
  • The runtime recenters the tracking origin on its own and re-localizes anchors as the room map improves, and each of those slides a one-shot alignment permanently out of the shared frame
  • Because World Root moves under the world grab
  • To keep the rig's height matched to the player's real height

The transform is idempotent by construction, so a frame in which nothing moved writes back the pose already there. It is yaw-only — pitch and roll from an anchor are noise — but it does take the anchor's height.

The anchor height-disagreement guard was raised from 0.25 m to 0.6 m. What was the bug?

  • It rejected frames during the world grab
  • It logged once per frame and flooded the debug box, hiding other messages
  • It applied pitch and roll along with the height
  • It rejected the very case the height correction exists to fix — a headset guessing the floor can be half a metre out, and because the check re-fails every frame such a headset never aligned at all

The startup race the tight bound was really guarding is now caught directly, by asking XROrigin whether tracking has reached Floor. And raising it in the .cs file alone does nothing — PersistentRig.prefab carries its own serialized copy.

RoomAnchor.worldHolder uses NoHolder = ulong.MaxValue rather than 0. Why does that matter?

  • 0 is the host's client id, so it would read as "the host is holding the board" at all times
  • 0 is the default value of an unset NetworkVariable and would not replicate
  • Client ids are signed, so 0 is ambiguous
  • Because the lock is server-written and 0 means "no write yet"

Without a lock at all, two players gesturing at once each stream a pose from their own hands and the board oscillates at the tick rate.

The world grab accumulates yaw from per-frame deltas instead of computing theta − theta0. What does the naive version do?

  • Drifts slowly, because floating-point error accumulates
  • Applies the rotation about the wrong axis when the hands are level
  • atan2 wraps at ±180°, which spins the board a full turn at the seam and caps the gesture at half a revolution
  • Rotates the rig instead of the content

Frames where the hands are stacked vertically contribute nothing, which reads as a pause in the turn rather than a spin. Scale is the clamped span ratio for a related reason.

The grab scales World Root and never the rig. Why is that not interchangeable?

  • Scaling the rig would break the ring radius
  • Scaling the rig drags the user's tracked hands away from the real hands they can see through passthrough
  • The rig is DontDestroyOnLoad and its scale is not replicated
  • Netcode refuses to replicate a non-uniform scale

The structural half: everything the game owns hangs under World Root and nothing a player owns does, which makes "move everything except the players" a fact about the hierarchy rather than a filter.

Passthrough comes up black. Which cause is the most common, per the project's own notes?

  • URP post-processing left on for the camera — the post stack writes opaque alpha into the final target
  • The skybox material was not removed
  • OVRManager is missing from the scene
  • The passthrough layer is set to Underlay instead of Overlay

All four conditions must hold: clear flags solid colour with alpha 0 and post-processing off, HDR off on all three URP assets (mobile HDR selects a format with no alpha channel), Underlay not Overlay, and no skybox. Removing the skybox alone gives you black with no error.

Why is the passthrough on/off state a static rather than a NetworkVariable?

  • It is set before any network session exists
  • Because OVRManager is not a NetworkBehaviour
  • It is a per-user comfort setting like brightness, and one player switching to VR must not drag the room with them
  • Replicating it would move the join config hash

Being static is also what carries the choice from the lobby into the game. The controller owns Guardian suppression alongside it, because Meta requires the two to move together.

PlayerControls and WorldGrab run at order 20 instead of the default 0. What does order 0 cost?

  • The board pose has not been replicated yet, so the grab starts from the origin
  • They sample head and hand world poses before the rig has moved, so every pose broadcast is a frame stale — about 13 ms at 72 Hz, on top of network latency
  • The anchor's world pose has not been refreshed by the SDK
  • Their OnNetworkSpawn would run before the player object exists

The whole chain, −10 through 30, exists to put everything that reads a world pose after everything that writes one.

Why must a hand-invoked csc always be given an explicit -out: pointing outside the repo?

  • Otherwise it writes into Library/ScriptAssemblies and the Editor rebuilds it
  • Because the output would be committed by .gitattributes
  • Roslyn refuses to run without one
  • Roslyn names the output after the first source file, and a tracked BoardAnchor.dll sits at the repo root — so compiling a list beginning with BoardAnchor.cs silently overwrites it

It then turns up as a modified binary in git status with no obvious cause. Use Unity's .NET Roslyn, not MonoBleedingEdge's csc.exe, which never reaches compilation.

In Stairs, where does the turn state live, and why?

  • On the seat, so out-of-turn play is impossible to express rather than merely refused
  • On the client, because Stairs has no turn order
  • On the board, alongside the tile heights
  • On RoomAnchor, so it survives a game switch

An RPC arrives, the server resolves the sender to a seat, and re-runs the rule against replicated state. Seats are never released once claimed.

A Stairs drag shows a ghost of the piece being moved. Why is the ghost cloned before the original is hidden?

  • So the clone inherits the original's network identity
  • To keep the original's collider live for the drop test
  • Cloning a hidden object clones it hidden — the ghost would be invisible
  • Because Instantiate cannot copy an inactive GameObject

A small ordering trap of exactly the kind this project documents rather than rediscovers. The view itself reconciles from replicated state on every change, never from the drag.

Plateau's movement graph is derived from bar geometry and then published by the server with a graphHash. What is the hash for?

  • So a client can tell that the graph it holds is the graph the server derived, rather than silently working from a different board
  • To seed the random bridge layout identically on every client
  • It is folded into the join handshake alongside the prefab set
  • To detect when a bridge has been re-laid without re-sending the whole graph

The derivation runs from authored geometry, so two clients on different builds could produce different graphs from the same scene — and the numbers are on the wire.

Plateau spawns no NetworkObjects of its own. What does it do instead, and what does that buy?

  • Each client simulates the board locally from a shared seed, so nothing needs replicating
  • It uses ClientNetworkTransform on pooled pieces owned by whoever moves them
  • Its state rides on the already-registered Room Anchor and its pieces are local visuals rebuilt from that state — so it never touches DefaultNetworkPrefabs.asset
  • It spawns its pieces with destroyWithScene: true, which keeps them out of the prefab list

Touching that list changes the prefab set, which ForceSamePrefabs folds into the join handshake — so it is global by construction. BASH does register two prefabs, because it needs per-object ownership.

Plateau tints many pieces per seat with a MaterialPropertyBlock, while one chooser prop assigns renderer.material directly. Why the difference?

  • MaterialPropertyBlock cannot set a colour on a URP shader
  • Reading renderer.material instantiates a copy of the material, which is right once for a single prop and wrong across dozens of pieces reconciled every frame
  • The chooser's material must be shared so every client sees the same colour
  • Property blocks are lost on a scene switch, and the chooser survives one

Same reasoning behind BASH's noted rough edge, where ChangeMaterial uses the instancing accessor on four renderers per base — harmless at that count, and the idiom both other games avoid.

In BASH, a player's ring slot is 6. Which base do they get, and why?

  • Base 6 — the ring slot is the base index
  • No base; only ring slots 0 to 3 have bases
  • Whichever base is unclaimed when the seating tick runs
  • Base 1, via BaseForRingSlot — slots 0, 6, 3, 9 map to bases 0, 1, 2, 3, the four ring slots where a base actually stands

PickFreeSlot hands out 0, 6, 3, 9 in that order, so the first four joiners still get bases 0–3 in join order. Treating the ring slot as a base index once left the second player with no base at all.

BASH sends a piece's final position as an RPC that names the piece, rather than writing it to a NetworkVariable. What failed before?

  • The variable was owner-written, so other clients rejected the write
  • An RPC is queued immediately while a variable delta waits for the end of the tick, so the deselect always arrived first and the pose was applied with nothing selected to receive it
  • A Vector3 cannot be stored in a NetworkVariable
  • The variable's OnValueChanged did not fire on the writer

The symptom was memorable: the trail appeared but the piece stayed on its old square, until its owner selected it again and republished a pose at a moment when something was selected. A message that depends on other state having arrived first is a message waiting to break.

Every Physics query in BASH passes QueryTriggerInteraction.Collide. What happens if one is left out?

  • It finds nothing at all, silently — every collider in that scene is a trigger and the default is Ignore
  • It throws, because the scene has no non-trigger colliders
  • It finds walls but not gamepieces
  • Nothing; Collide is the default for RaycastNonAlloc

An expensive no-op with nothing in the console: the wall rule stops working, or the shell stops killing anybody.

BASH raycasts each trail segment as it is drawn instead of trusting the trail's trigger callbacks. What made that necessary?

  • A MeshCollider cannot raise trigger events for a non-convex mesh
  • Trigger callbacks do not fire on the client that owns the object
  • A trigger is only tested on a 50 Hz physics step, and late in a shot the tip covers ~0.2 board units per frame against a 0.04-thick wall — so a shot can cross a wall between two steps and be released before any step looks at it
  • The trail's collider is disabled while the trigger is held

And nothing looks afterwards, because the commit clears checkForCollisions on the way out. The two sweep loops are also ordered deliberately: find the nearest blocker first, then kill only what lies at or before it.

You raise a tuning constant's initializer in a .cs file and nothing changes at runtime. Why?

  • The assembly was never recompiled — check the ScriptAssemblies timestamp
  • A serialized value wins over the field initializer, and a prefab or scene carries its own copy of it
  • The field is const and was inlined at its call sites
  • The value is replicated and the server's copy overrides yours

The worked example is the anchor height guard on PersistentRig.prefab. The sibling trap: renaming a serialized field drops every scene's value silently.

Which change obliges you to reflash every headset from the same build before anyone can play together?

  • Adding a row to GameCatalog.asset
  • Adding a menu action to a GameModule
  • Changing a serialized default on a scene object
  • Adding a prefab to DefaultNetworkPrefabs.asset, or editing Player.prefab

Both move the join handshake's config hash, and the refusal carries no reason string — it shows up as a join that hangs for ever. Ask first whether the object needs to be a NetworkObject at all.

Terms as this project uses them. Where a word has a general Unity or Netcode meaning and a narrower one here, the narrower one is what is written down.

alpha 0
The background alpha a frame must have for the Meta runtime to composite the camera feed underneath it. Four separate settings have to agree; see Module 14.
Bash Root
BASH's content frame, a child of Board. Every networked BASH value is expressed in its local space, through four conversion helpers.
base
BASH's per-player object, carrying four gamepieces. Spawned owned by its player and parented to Bash Root. Not the same thing as a ring slot.
board-local
Measured in the content frame rather than in world space, so the value survives the world grab. The convention in Plateau, Stairs and BASH alike.
Camera Offset
The XROrigin child that must be zeroed once tracking reaches Floor. A standing adult reading head.y ≈ 1.36 or ≈ 2.7 means it never was.
ClientNetworkTransform
A NetworkTransform with OnIsServerAuthoritative() => false, twelve lines long, so a player's avatar is driven by the player.
colocation
Several headsets in one real room agreeing on one physical frame, by each moving its own rig so a shared spatial anchor lands on the world origin.
ColocationProbe
The 1 Hz readout that says whether colocation is working. Currently enabled in every build — turn it off before debugging anything else.
config hash
What a joining client sends and the host compares: NetworkConfig plus every registered prefab's GlobalObjectIdHash. A mismatch is refused with no reason string.
connection approval
The server callback that inspects a joiner's ConnectionPayload — name, owned mask, build — and may refuse with a readable reason. Switched on from code in RoomApproval.Prepare.
content frame
World Root. Everything the game owns hangs under it and nothing a player owns does, which is what makes the world grab structural rather than a filter.
dcad7e9
The last commit of Math Classroom, the different application this repo's history begins as. git blame before it is not about this project.

The registered prefab set. Global by construction, because ForceSamePrefabs folds it into the join handshake. Must hold only prefabs under Assets/.
[DefaultExecutionOrder]
The attribute fourteen components use to guarantee that everything reading a world pose runs after everything writing one. Values −10 to 30; see Module 15.
destroyWithScene
The Spawn argument deciding whether a spawned object survives a LoadSceneMode.Single switch. false for the room anchor and the players, true for a BASH base.
dtls
The default Relay transport protocol here. It must match on host and joiner or the join fails.
ForceSamePrefabs
The Netcode setting, on in this project, that refuses a client whose prefab set differs. The reason it is a rule that both headsets are flashed from the same build.
GameCatalog
The list of GameModules at Assets/Resources/GameCatalog.asset, loaded by name because nothing that needs it has an Inspector slot a scene could fill.
GameModule
One ScriptableObject per game holding everything shared code needs to know: menu key, scene, label, rules, extra keys — and the store half.
GameRoutes
A thin façade over the catalog (DefaultScene, IsGameKey, IsGameScene, TryGetScene). It is what a client-supplied key is validated against.
GameSessionRegistry
Where games register themselves. ForKey for "the room is switching to this"; Active for "the game on screen now". Conflating the two is a bug.
gamepiece
In BASH, one of four children of a base — boat 0, plane 1, sub 2, helicopter 3. The kind is the sibling index, and that integer travels in every RPC.
graphHash
Plateau's check that the movement graph a client holds is the one the server derived from the board geometry.
group GUID
The identifier an OVRSpatialAnchor is shared into. Published on RoomAnchor alongside the anchor's UUID for every other client to download.
HierarchyUtils
The shared name-based hierarchy search, replacing four private copies — one of which BASH was borrowing across the game boundary. Named this way because Unity 6 added a Unity.Hierarchy namespace.

The one client that is also the server. There is no dedicated server, which is why the library gate is a social rule and not DRM.

The only thing shared code is allowed to know about a game: OnGameSelected, InvokeMenuAction, AvatarBadgeForSeat. Returning null is the normal answer.
keyInfo
The renderer-agnostic component on anything pressable: it swaps a Material on a mesh and tints a Graphic through one Apply(bool).

A pressable's stable string id — the thing dispatch is keyed on, never a slot index. ScrollUp and ScrollDown are reserved.
libraryBit
A game's bit (0–63) in the owned mask that travels on the wire. Stable for ever, never reused, and never the catalog index. 0 Stairs, 1 Chasms, 2 BASH.
Lobby
Unity Lobby, used here as a directory over the unchanged Relay flow and nothing more: the host publishes its join code, a browser reads it back.
LocalIsAligned
The static that says this client is colocated. Once true, joystick locomotion, snap-turn, recentring and the debug tilt all early-out — a colocated player's position is a fact about the real room.
MaterialPropertyBlock
How per-instance tints are set without instantiating a material per renderer. Reading renderer.material copies the material, which is right once and wrong across dozens of pieces.
NetworkList
A replicated list. Its initial contents raise no OnListChanged, so every view rebuilds from current state in OnNetworkSpawn as well as on change.
NetworkVariable
A replicated field. Its write permission is this project's security boundary; its delta is sent at the end of the tick, which is why an RPC can overtake it.
NoHolder
ulong.MaxValue, the world-grab lock's "nobody" value. Not 0 — that is the host's client id.
OnNetworkSpawn
Where a NetworkBehaviour wires itself up and reconciles from current state. It can run later than the connect callback, which is why several systems poll at 4 Hz instead.
OnValueChanged
A NetworkVariable's change callback. Raised synchronously on the writer — which BASH's FreezeSpin depends on — and not raised for the value a client arrives with.
owner-written
A NetworkVariable the owning client writes directly. Reserved for things that genuinely are facts about their owner: hand and head poses, BASH's aim.
passthrough
The real room, shown by a compositor layer the Meta runtime owns — not a render feature. The app's job is to submit a frame with nothing in the background.
PersistentRig
The one prefab holding XRRig, the hands, Input Reader, Menu Manager and the light. One instance, in OpeningScene, for the life of the app.
phyllotaxis
The golden-angle spiral Plateau lays pieces out with, so any number of them packs evenly on a plateau without a special case per count.
plateau index
Sibling order under Plateaus, and it is on the wire. Reordering those 41 children renumbers the board; appending at the end is safe. Stairs' Cells works the opposite way.
PointerBeam
The order-24 component that does one Physics.SyncTransforms() and one raycast, and publishes the hit for every selection script to read that same frame.
pointerControl
The other targeting system: a trigger capsule on the beam that reports colliders tagged key and, in BASH, gamepiece.
productId
The string keying a player's saved library, which outlives app updates. Stable for ever, never reused, never the catalog index.
QueryTriggerInteraction.Collide
Mandatory on every physics query in BASH, where all the colliders are triggers. The default finds nothing at all, silently.
Relay
Unity's relay service, allocated for 12 here. The whole join flow is Relay; Lobby only advertises the code.
reflash
Build and install on every headset from the same build, because something moved the config hash. The alternative is a join that hangs on "Joining room…" for ever.
ring slot
A player's place on the 12-slot, 2 m ring, assigned once by PickFreeSlot and held in spawnSlot. Never re-spaced. Not a seat, and not a BASH base index.
RoomAnchor
The room's own replicated object, spawned destroyWithScene: false: the anchor identity, the content pose, the world-grab lock, the room kind — and Plateau's whole board.
RoomContent
The order-15 component on World Root that applies the replicated board pose with an 80 ms filter, snapping rather than gliding on the first frame.
seat
A game-side playing position, distinct from a ring slot. Stairs has two and never releases them; BASH has four and maps them from ring slots; Plateau keys pieces and colours by seat.
SenderClientId
From ServerRpcParams.Receive. What every mutating ServerRpc validates, because RequireOwnership = false means anyone can call it.
server-written
A NetworkVariable only the server may write. The default for anything a client must not forge: spawnSlot, playerName, ownedMask, everything on RoomAnchor.
ServerTime
The clock every client shares. BASH derives its spinning aim from it plus one owner-written start time, instead of streaming the heading every tick.
similarity transform
The uniform-scale-plus-rotation-plus-translation the world grab applies, mapping the gesture's start centre onto its current one. Naive translation drags the board sideways.
spectator
A player with a ring slot but no seat — a fifth player in BASH, a third in Stairs. Every game path tolerates it rather than checking once.
Physics.SyncTransforms()
Needed before any physics query run from Update here, because the content frame is still being smoothed and m_AutoSyncTransforms is off. Three call sites, one reason.
tick rate
30 Hz. The rate NetworkVariable deltas are sent at, against a headset rendering at 72–90 — which is why remote poses are smoothed and why an RPC can arrive before a delta.
TrySetParent
Netcode's runtime parenting call, which replicates the new parent together with the local transform. How a BASH base ends up under Bash Root on every client.
UI unit
1 mm. Every Canvas in the toolkit is at localScale 0.001, so a 1200-unit panel is 1.2 m and an 84-unit row pitch is 8.4 cm.
underlay
The OVRPassthroughLayer mode that puts the camera feed beneath the rendered frame. Overlay draws it on top of everything.
Vivox
Voice. One group audio channel per room, named after the room code. Toggled from the menu by the host, and the toggle shows its state.
world grab
Both grips: move, turn and resize the board. Server-locked to one player at a time, applied as a similarity transform, and it scales the content and never the rig.
XROrigin
Unity's XR rig, used here instead of OVRCameraRig. Its CurrentTrackingOriginMode reaching Floor is the gate on colocation being meaningful.

Rotating the rig about Y alone to match the shared anchor. Pitch and roll from an anchor are noise and applying them would tip the board off the real floor — but the anchor's height is used.
